Humans should prompt their AI agent, not manually drive a complex CLI. The agent resolves intent, source, scope, version, and path, then uses llm-docs as a deterministic capability layer. When users ask for source-truth codebase docs, the agent must choose that workflow explicitly and preserve source-file provenance.

North Star

The tool should not be timeless because URLs never change. It should be timeless because it records inspectable evidence, reports when explicit sources move, and tells the agent when no reliable source was found within the requested scope.

The Real Problem

Official docs may be correct, but they are usually shaped for browsers instead of agent memory.

Registry Fragility

config/sdks.json stores hardcoded paths and raw URLs. If Supabase moves a spec file, the configured path becomes wrong. A cache might hide the issue, but that creates stale output instead of fresh output.

Stale path risk Silent cache risk

Local Source Mode Is Passive

Local source mode can parse a markdown directory, but it does not clone a repo, search for docs, inspect package metadata, or decide which source is authoritative.

Needs local files No discovery

No Provenance Contract

Generated docs need a machine-readable record of source URL, repo commit, input path, content hash, parser version, and freshness checks. Without that, users cannot trust when the output was current.

Trust gap Needs manifest

Official Docs Still Need Processing

Official docs are the preferred source for explanations, examples, and intended usage, but implementation source code is the final authority for APIs and behavior when verification is requested. The tool should preserve official docs while optionally flagging claims that conflict with source code.

The Human Interface Is The Prompt

The user should ask their AI agent for a docs pack. The agent should decide whether to use official docs, local docs, repo docs, or source-truth codebase docs, then call the CLI with the right mode and report the manifest warnings.

Product reframing: this repo should become a deterministic inspection, extraction, conversion, and verification capability layer for AI-agent docs packs. The AI agent owns judgment-heavy intent and source selection; the existing parser and formatter are the conversion engine, not the whole product.

Next-Gen Architecture

Separate agent judgment from deterministic CLI inspection, conversion, and reporting.

Layer 1 Input Normalizer
Layer 2 Bounded Inspection
Layer 3 Candidate Evidence Report
Layer 4 Parser and Formatter
Layer 5 Verification Manifest
Input Normalizer

Accepts explicit inputs from the agent or user, such as a GitHub repo URL, docs website URL, local path, manifest path, SDK language, or version. It normalizes syntax into a target object and reports missing or ambiguous fields instead of silently deciding the authoritative source.

Bounded Inspection

Given explicit source and scope, clones or updates repositories in a stable cache, lists and groups candidate docs files, inspects explicit URL resources and fixed same-origin metadata resources, extracts links from fetched content, checks llms.txt and sitemap.xml, and records what was inspected.

Candidate Evidence Report

Produces a candidate evidence report for observed candidates. The CLI records factual signals such as file type, path, metadata, source URL, hash, freshness metadata when explicitly observed, parseability, and explicit user-provided scope, then deterministically orders the report for agent review without deciding authority, correctness, source truth, task fit, source intent, or whether a candidate satisfies the user task.

Parser and Formatter

Reuses the current core: OpenRef parser, Markdown/DocC parser, universal DocNode model, and agent-docs formatter. Add OpenAPI, MDX cleanup, RST, and HTML extraction as separate parser modules.

Compatibility Baseline

Keep the proven Supabase/OpenRef workflow covered while the new input normalizer grows. The old generate --sdk, list-sdks, and validate --sdk behavior may become compatibility aliases later, but it must not break silently.

Verification Manifest

Writes a manifest with source path, commit hash, content hash, parser, generated files, source-code verification status, conflicts, verification timestamp, and warnings. This is the basis for refresh, diffing, and trust.

How A Run Actually Works

The next-gen tool should make every explicit input converge into the same inspectable pipeline.

1. Accept Target

The human gives the AI agent a task in plain language. The agent turns the product name, GitHub repo, package name, docs website, local path, or manifest into a typed target and records any ambiguity before touching sources.

2. Resolve Source Scope

The agent resolves scope, version, source intent, and candidate judgment before generation. For repo inputs, use the repo directly. For website inputs, the CLI can inspect canonical links, footer links, GitHub links, llms.txt, sitemap.xml, and package metadata within the requested scope and report the evidence back to the agent.

3. Cache And Inspect

Clone or update repositories in ~/.explore/repos/<owner>__<repo>. Never clone into the active workspace by default. Inspect README, package files, docs folders, config files, and framework metadata before reporting candidates.

4. Report Candidates

Give every observed docs source a factual evidence record based on observed source/provenance signals, structure, explicit user-provided scope, path, metadata, source URL, hash, freshness metadata when explicitly observed, and parseability. Generate only from a user-provided source, an agent-provided candidate, or a documented automation flag; otherwise produce a candidate evidence report for agent inspection.

5. Convert

Parse the explicit agent/user-selected source into the shared DocNode tree, format it into agent-optimized Markdown, chunk by semantic boundaries, and preserve stable section IDs for repeatable references.

6. Verify Output

Re-open generated files, check hashes, validate manifest references, estimate token counts, and report warnings. A generation run is incomplete until it can explain exactly what it used.

Input Decision Matrix

Different user inputs need different first moves. This matrix should be encoded in the agent skill, while the CLI mirrors the deterministic validation and reporting pieces. Humans should normally express intent in prompts; these routing rules are for the agent to choose and the CLI to execute only with explicit inputs. 

GitHub repo URL -> clone/update cache -> inspect explicit repo scope -> agent reviews candidate evidence report
Docs URL        -> inspect llms.txt/sitemap/source links within URL scope -> agent reviews candidate evidence report
Package name    -> agent resolves package metadata to explicit repo/docs -> CLI validates
Product name    -> agent investigates official website/repo -> ask if ambiguous
Local path      -> no discovery unless --discover-neighbors is set
Manifest path   -> verify/refresh exact prior source

Evidence Policy

The system should avoid acting certain when inspection is weak. The CLI reports factual evidence and deterministic ordering; the agent inspects candidates in light of the user task, project context, version constraints, and source intent. If no candidate is authoritative for the task, the agent continues investigation, chooses another explicit source, or asks the user. 

explicit source/candidate supplied: generate or validate that exact input
candidate evidence report only: do not generate by default
multiple plausible candidates: agent reviews source intent, version, and project context
no authoritative task source: agent investigates another explicit source or asks the user

What Makes It Timeless

The tool should handle change instead of pretending change will not happen.

Registry As Hints

Keep a registry, but downgrade it from authority to shortcut. A registry entry means "try this first," not "trust this forever." Every hinted path must be verified before use. 

{
  "target": "github:supabase/supabase",
  "hints": [
    "apps/docs/spec/supabase_swift_v2.yml",
    "apps/docs/spec",
    "apps/docs"
  ],
  "preferredFormats": ["openref", "openapi", "markdown"]
}

Reality Checks

Before generation, the tool should check if the source exists, if it changed since the last run, and if the parser still understands it. If not, it re-runs bounded inspection within the explicit source scope. 

llm-docs verify supabase/supabase

checks:
  - source path exists
  - repo commit changed
  - content hash changed
  - parser still succeeds
  - generated manifest matches output files

Version And Cache Semantics

External repos must be reused safely, compared against remotes, and checked out according to user intent.

Cache Comparison

The repo explorer should compare an existing cached clone against the requested remote before using it. It should fetch refs, compare commits, detect dirty state, and avoid destructive updates. 

cache: ~/.explore/repos/tailwindlabs__tailwindcss
checks:
  - origin URL matches requested repo
  - working tree is clean or preserved
  - remote refs fetched
  - HEAD compared with requested branch/tag
  - manifest records commit and dirty state

Latest Versus Pinned

"Latest" and "pinned" are different product decisions. If the user chooses Tailwind 3, the agent must not silently move them to Tailwind 4 just because v4 is current. 

user says "latest"       -> resolve current stable release/default docs
user says "Tailwind 3"   -> resolve latest compatible v3 tag/branch
user gives tag/branch    -> checkout exactly that ref
user gives commit        -> checkout exactly that commit
ambiguous release lines  -> ask before generating

CLI Design For Agents

Commands should make the lifecycle explicit for the agent: discover, generate, verify, refresh.

Discover A GitHub Repo

Clone or update the repo cache, inspect files within scope, and write a candidate evidence report for agent review.

llm-docs discover https://github.com/supabase/supabase
llm-docs discover supabase/supabase --sdk swift
llm-docs discover supabase/supabase --format openref

Generate From Explicit Source

Use an agent-supplied source, candidate, or manifest, then write an agent-readable Markdown pack plus manifest. Future discovery-report input must require an explicit agent/user-selected candidate or a documented automation flag; the current CLI does not select candidates from discovery reports or generate directly from URLs. 

# future/planned: requires explicit candidate selection or documented automation flag
llm-docs generate --source ./reports/supabase/discovery-report.json --candidate apps/docs/spec/supabase_swift_v2.yml
llm-docs generate --source ~/.explore/repos/swiftlang__swift-book/TSPL.docc --format markdown
llm-docs generate --source ./exports/community-guidelines.html --format html

Generate From Known Local Source

Keep local source mode for deterministic use when the user already knows the docs directory.

llm-docs generate --source ./docs --format markdown
llm-docs generate --source ./openapi.yaml --format openapi
llm-docs generate --source ./Guide.docc --format markdown

Refresh And Verify

Check previous outputs against recorded source metadata, update explicit caches when allowed, and regenerate only when needed.

llm-docs verify supabase/supabase
llm-docs refresh supabase/supabase
llm-docs diff supabase/supabase --since last

Skill Integration

The skill should guide an AI agent from human intent to the right CLI workflow. The repo should do deterministic work.

Ship A Built-In Skill

Add a skill folder such as skills/repo-docs-discovery/SKILL.md. It should instruct agents to cache repos, inspect local instructions, search with rg, prefer source docs over rendered pages, and run the CLI. 

name: repo-docs-discovery
description: Discover current documentation sources for a repo, website, package, or product, then generate an AI-agent docs pack.

Use this skill when the user asks to generate, refresh, verify, or inspect documentation for an external target.

Agent Flow

The agent handles ambiguity from natural language prompts: if the user provides only a product name, the agent investigates the official repo or docs site before calling the CLI. If multiple candidates exist, it explains the tradeoff or asks the user when the choice is risky. 

1. Normalize target.
2. Check ~/.explore/repos cache.
3. Clone or update if needed.
4. Inspect repo metadata and docs.
5. Run llm-docs discover.
6. Review the CLI candidate evidence report and choose an explicit source.
7. Run llm-docs generate with explicit source/scope.
8. Report source provenance and warnings.
Boundary: the skill should not replace the CLI. The agent orchestrates discovery and judgment. The CLI remains scriptable and reproducible: it ingests explicit sources, performs bounded inspection, writes reports and manifests, and fails honestly.

Edge Cases And Required Behavior

The tool should fail explicitly when evidence is incomplete, not produce false authority.

Docs Path Moved

Verify the hinted path. If missing, re-inspect the explicit repo scope. If a replacement is found, update the discovery manifest and mark the registry hint as stale.

RediscoverWarn user

Repo Has No Docs

If the user wanted official docs, report "no documentation source found." If the user wanted source-truth codebase docs, run that mode when implemented; otherwise fail honestly and explain the missing capability.

No fake outputAnalyzer gated

Official Docs Conflict With Source

When source-code verification is requested and official docs disagree with implementation, preserve the official-doc context but mark the claim as disputed, cite the source files, and prefer the implementation for API signatures, config defaults, routes, and runtime behavior.

Conflict warningSource wins

Multiple Candidate Docs

Report factual evidence for each candidate in deterministic order. The agent inspects the user task, project context, version constraints, and source intent; if no candidate is authoritative for the task, it continues investigation, chooses another explicit source, or asks the user.

Evidence orderPossible prompt

Website But No Repo Link

Check llms.txt, sitemap.xml, canonical tags, robots.txt, and package metadata within the explicit URL scope. If no source is found, stop at the candidate evidence report or use an explicitly approved HTML extraction workflow, and record that output came from HTML.

HTML fallbackLower confidence

Single Policy Or Guidelines Page

Preserve visible "updated" dates, canonical URL, page title, and extraction timestamp. Treat it as policy/reference content, not SDK documentation, and avoid splitting it into artificial API-style categories.

Policy modeDate preserved

Private Repo Or Auth Required

Use the user's local Git credentials if available. Never embed tokens in manifests. If access fails, report the required permission instead of retrying blindly.

No token leaksAccess report

Generated Docs Are Huge

Docs Are JavaScript-Rendered

Prefer the source repo. If only rendered HTML exists, use a browser-based extractor as a fallback and record that the source was rendered HTML.

Docs Contain Old Version Pages

Detect version folders and version selectors. Let the user request a version, and include version provenance in output names and manifests.

Version awareNo accidental latest

Validate content type and parseability. If a configured "spec" URL returns a docs page, reject it as a spec and write a website inspection report instead.

Record source license when discoverable. Respect robots policy for crawling websites. Repository source parsing is separate from website scraping and should still record license data.

Treat docs as untrusted input. Do not execute examples, package scripts, or embedded commands during parsing. Escape output where needed.

MVP Boundaries

Clear non-goals keep the project useful instead of turning it into a vague universal crawler.

MVP Must Do

  • Accept GitHub repo URLs, docs website URLs, local paths, and existing manifests.
  • Clone or update GitHub repos in a stable external cache.
  • Discover OpenAPI, Swagger, OpenRef, markdown, MDX, DocC, RST, llms.txt, and sitemap candidates.
  • List, group, filter, and deterministically order observed candidates using factual evidence signals for agent review.
  • Generate agent-optimized Markdown only from explicit sources, explicit agent/user-selected candidates, or documented automation-flag candidate handling, and write manifest, candidate evidence report, and failure report artifacts for the relevant workflow.
  • Support source-code verification of official docs when the source repo is available and the user asks for source-truth confidence.
  • Distinguish repo docs conversion from source-truth codebase docs generation, and fail clearly if the requested mode is not implemented.
  • Verify old outputs against source existence, commit hash, content hash, and parser success.

MVP Must Not Do

  • Invent unverified documentation from implementation when that generator is missing or disabled.
  • Execute examples, package scripts, docs build scripts, or arbitrary repository commands.
  • Bypass authentication, scrape private content without user-provided access, or store tokens.
  • Claim a docs website is authoritative when only a noisy HTML extraction succeeded.
  • Generate from a discovery report's first or leading candidate without explicit candidate input or a documented automation flag.
  • Silently use stale cache content when current source verification fails.
  • Mix unrelated SDKs or products in one output just because they share a monorepo.

Implementation Roadmap

Build this in layers so each phase improves reliability without blocking on the full vision.

Phase 0

Stabilize Current Repo

Confirm the current type-check, build, test, and CLI baseline before expanding scope.

  • Fix any broken exports or CLI wiring found during baseline checks.
  • Add acceptance tests for OpenRef generation, markdown generation, list-sdks, and validate --sdk.
  • Make uncommitted local path changes either configurable or remove them.
  • Document current supported inputs honestly.
  • Preserve current Supabase/OpenRef output files or document an intentional migration path.
Phase 1

Registry Hints And Verification

Keep the registry but stop trusting it blindly.

  • Rename registry concepts from "known sources" to "hints."
  • Add source existence checks before generation.
  • Add content hash and generation manifest output.
  • Add llm-docs verify for existing outputs.
Phase 2

Repo Discovery

Implement the cache and repo inspection workflow inspired by the screenshots.

  • Add llm-docs discover <repo>.
  • Clone or update repos under ~/.explore/repos.
  • Search for docs directories, specs, markdown, MDX, DocC, and OpenAPI files.
  • Write candidate evidence reports.
Phase 3

Website Discovery

Support docs URLs and product pages without pretending every website is a clean source.

  • Check /llms.txt, /sitemap.xml, and canonical links.
  • Detect GitHub source links from docs pages.
  • Add HTML extraction fallback with lower confidence.
  • Record crawl policy and source type in manifests.
Phase 4

Parser Expansion

Support the formats discovery will commonly find.

  • Add OpenAPI and Swagger parser.
  • Improve MDX cleanup for framework-specific components.
  • Add RST support for Python-style docs.
  • Add semantic chunking with stable chunk IDs, including an opt-in JSONL source export.
Phase 5

Source-Truth Codebase Docs Generation

Support users who want agent-optimized docs generated from, or verified against, the implementation itself.

  • Add an explicit source-truth codebase docs mode; this is documentation generation, not a vulnerability audit.
  • Study the codebase diligently and extract public APIs, routes, exported types, config, examples, tests, and behavior constraints into structured facts.
  • Verify existing documentation claims against source code and flag conflicts where the implementation disagrees.
  • Allow official-docs generation to request source-code verification for API and behavior claims without switching the whole run to code-only docs.
  • Record every source file used for each generated section.
  • Refuse unverified summaries when evidence is incomplete or source verification is missing.
Phase 6

Distribution And Agent Installer

Make the tool discoverable when the user is working in a different directory or project.

  • Bundle agent context and skill files in the npm package.
  • Add llm-docs agent context and read-only llm-docs agent doctor; keep llm-docs agent install codex planned until host mutation is explicit and supported.
  • Document that installing the CLI and registering skills are separate operations.
  • Make llm-docs capabilities --json expose implemented modes.
Phase 7

Agent Skill Package

Make the repo usable by AI agents as a guided workflow, not just a CLI.

  • Create skills/repo-docs-discovery/SKILL.md.
  • Include discovery rules, cache rules, candidate evidence report handling, and failure handling.
  • Add examples for repo URL, docs URL, package/product name, and local path inputs.
  • Maintain index.md and AGENT_CONTEXT.md as the agent crawl map and intent contract.
  • Keep skill instructions separate from parser logic.

Success Criteria

The upgraded repo should be judged by correctness, freshness, and explainability.

Freshness

Every generated output can be traced to a repo commit, content hash, or website fetch timestamp.

Recoverability

If a docs path moves, the tool re-runs bounded inspection and reports exactly what changed.

Honest Failure

If no docs exist, the tool says so clearly instead of manufacturing low-confidence output.

Scriptability

Everything the skill can do should also be possible through deterministic CLI commands.

Extensibility

New parsers can be added without rewriting discovery or formatter logic.

Low Workspace Noise

External exploration happens in a stable cache, not inside the user's active project.
